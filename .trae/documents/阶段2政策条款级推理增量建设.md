# 阶段 2：政策条款级推理增量建设

## 1. 摘要与目标

依据 `kg-system/ontology_ly/方案定稿.md`、`STAGE0-执行分解.md`、`packs/policy/stage2b_口径句清单.md` 和 `packs/policy/clause_model.json`，本阶段按两个可独立验收的增量实施：

1. **增量 A：2a/2b 契约收口**。保留现有政策现行有效、Scope、版本链和条款抽取主链路，补齐版本边界回归、冻结分类优先级、原文偏移、稳定身份、主/例外条件隔离和重抽保护。
2. **增量 B：2c 推理技术验收**。将主服务从 Cozo 骨架迁到 **Nemo 0.10.1**，以 `POL0001`《关于公布2025年稻谷最低收购价格的通知》为端到端技术样本，完成一级政策清单过滤、statement 级三态判定、完整证明链、统一 API 和隔离评测。

本轮只交付 `technical-smoke` 证据。自动抽取和自动编译结果保持 `DRAFT`；不得伪造专家确认、专家测试用例或业务金标。没有独立专家材料时，即使技术门禁全部通过，也必须写明 `businessQualityGate="NOT_ASSESSED"`，不得宣布政策业务验收完成。

## 2. 当前状态与问题边界

### 2.1 可直接复用

- `app/policy.py` 已实现统一 `asOf`、状态分类、Scope 覆盖、版本链和 `P1..Pn` 引用。
- `app/pack2b.py` 已实现条款切分、六类陈述、模糊词、条件/例外/后果/参数抽取及入库。
- `seed/mapping.json` 已有 `NormativeStatement.confirmedBy/confirmedAt`、`CompiledRule.backTranslationMatch/testcaseIds/confirmationStatus` 和 `RuleTestCase` 所需字段，无需盲目扩表。
- `packs/policy/rule_trial/` 已有 Nemo 单条款 7/7、多条款 11/11 的构造样本试验，可复用事实注入、空谓词哨兵、优先级闭包和成环检测方式。
- `ontology_ly/tools/evaluate_stage1.py` 已提供 SQLite 快照、临时 `data_dir`、前后 SHA-256、逐案结果和硬门禁模式。
- 阶段 1 的检索、引用、别名、Scope/Kùzu 基线已完成，本阶段只回归，不重建或调权。

### 2.2 必须先以回归证实并修复的风险

- `app/policy.py` 对未发布、非法日期、已失效或已废止后继版本的取代边界缺少覆盖。
- `app/pack2b.py` 当前分类顺序把 `DEFINITION` 放在最后，与冻结优先级相反；重抽使用递增 statement ID，无法保证 CompiledRule、RuleTestCase 和专家复核关联稳定。
- 当前重抽/重编译清理未完整保护非 DRAFT 规则和专家测试；主条件与例外条件共用 `statementId` 命名空间，下游可能混读。
- `app/pack2c.py` 自称 skeleton，一级政策过滤计算后未使用，主模板仍是 Cozo，且部分谓词命名不一致。
- `app/rule_engine.py` 的集合比较可能把缺事实返回为真；非法数值、未知比较符、例外未知和引擎异常可能丢失 `UNABLE` 语义。
- `app/conclusion.py` 按 `clauseId` 建单值字典，会折叠同一条款下的多条 statement/rule；正式路径证明链不完整，混合 fallback 的引擎标识也不清晰。
- `requirements.txt` 尚未声明 Nemo；当前测试中的手工 `CONFIRMED` 只验证路径开关，不是专家证据。

## 3. 路径比较与选择

- **方案一：直接垂直打通 2c**。改动较少，但会把不稳定 ID、2b 分类冲突和专家资产误删风险带入规则层，排除。
- **方案二：一次性重写政策、图查询和推理全链路**。边界过大，会破坏阶段 1 与现有 API，排除。
- **方案三：两增量收口，推荐**。先用测试固定 2a/2b 契约，再以一份一级政策接入 Nemo 和隔离评测；每一步都有可回滚、可审计证据，本计划采用此方案。

## 4. 实施内容

### 4.1 固化依赖、一级政策清单与规则资产

**修改：`kg-system/requirements.txt`**

- 增加 `nemo-python==0.10.1`，实际验证 `import nmo_python as nemo`、字符串规则加载、`reason()` 和 `result()`。
- 主服务不依赖本机未声明的 Cozo 安装；本增量不做 Cozo 自动降级或双引擎静默切换，既有 Cozo 试验资产仅保留作选型溯源。

**新增：`kg-system/ontology_ly/packs/policy/tier1_policy_registry.json`**

建立版本化只读清单，不用 `policyLevel=="部门规范性文件"` 代替一级政策判定。每条记录包含 `policyId`、文号、三项资格证据、量化条款 ID 和清单版本。首条仅纳入 `POL0001`，明确记录：

1. 国家发展改革委等中央部委发文；
2. 全国统一的最低收购价参数；
3. `POL0001-C001..C003` 含品种、每 50 公斤和具体价格。

编译器只接受清单内政策；未收录或二级政策不得生成 CompiledRule。清单不提供运行时任意增删 API。

**新增：`kg-system/ontology_ly/packs/policy/rules/stage2_nemo.rls` 与 `rice_minprice_2025.rls`**

- 前者保存通用的 Nemo 三态、例外和优先级规则模板，沿用试验中的 `__NONE__` 空谓词哨兵。
- 后者保存 `POL0001` 技术样本的确定性编译结果，由同一编译逻辑生成，不手写另一套政策阈值。
- 测试校验 `rice_minprice_2025.rls` 与 POL0001 对应 CompiledRule 的规则集合一致，且共享模板确为 `stage2_nemo.rls`；Nemo 缺失或规则加载失败必须显式失败，不得 skip 后宣称通过。

### 4.2 增量 A：2a 现行有效与版本链边界回归

**修改：`kg-system/tests/test_policy.py`；必要时最小修改 `kg-system/app/policy.py`**

新增以下时点用例，先观察现有行为，再只修复失败项：

- 后继 `UNPUBLISHED`、`NOT_YET_EFFECTIVE` 或生效日期非法时，不得提前取代当前版本。
- 后继已经生效、随后到期或废止时，历史取代关系仍成立，旧版本不得因此“复活”；该时点可以没有 CURRENT 版本。
- 多跳版本链在同一 `asOf` 下只返回可证明的当前版本，非法日期不猜测。
- 既有 Scope 覆盖、未知 Scope、`citationIndex` 和引用编号行为保持不变。

### 4.3 增量 A：2b 分类、原文偏移与稳定身份

**修改：`kg-system/app/pack2b.py` 与 `kg-system/tests/test_pack2b.py`**

1. 将分类冲突顺序固定为 `DEFINITION > TARGET > PROHIBITION > OBLIGATION > PERMISSION > AUTHORIZATION`。无模态的“2025年粮食产量为7000万吨”按 DEFINITION；TARGET 测试改用含明确目标模态的文本，并验证 TARGET 高于 OBLIGATION。
2. `vaguenessFlag` 只使用冻结十词：`适当、必要时、有关部门、原则上、及时、视情况、酌情、合理、相应、必要`，记录实际命中词，不扩词、不自动确认。
3. 自动抽取继续保持 `actorScopeId/objectFormIds/regionalScopeId=null`，2b 不产出 ClauseRelation，不运行规则编译。2b 冻结清单作为总模型必填字段在自动抽取阶段的明确例外，不得为填字段而猜测 Scope 或 actionVerb；actionVerb 无法从原文确定时在 DRAFT 中保持 null，并在正式确认校验中拒绝该陈述。
4. 修正切片与偏移一致性：保存的 statement 文本必须等于 `clauseText[charStart:charEnd]`，quote 可逐字回链；针对前后空白、多陈述和中英文标点增加回归。
5. statement ID 改为确定性身份：对 `{clauseId, charStart, charEnd, text}` 使用 UTF-8、键排序、无多余空白的规范化 JSON 计算 SHA-256，取前 32 位小写十六进制并加 `STM-` 前缀。相同输入重抽 ID 不变；文本或偏移改变则生成新身份，不覆盖旧专家资产。
6. `NormativeStatement.conditionId` 只指向主条件根，`ClauseException.conditionId` 指向例外条件根。编译与判定分别读取对应子树，不得再把同一 statementId 下全部条件当作主条件。当前只承诺扁平 LEAF；遇到未支持的 AND/OR/NOT 结构必须返回 UNABLE，而非猜测。
7. ClauseConsequence 仅在显式动作与量值同时存在时生成；纯 DEFINITION 的数值只进入 RuleParameter。用 TARGET、PROHIBITION、DEFINITION 反例固定边界。

### 4.4 增量 A：重抽/重编译幂等与专家资产保护

**修改：`kg-system/app/pack2b.py`、`app/pack2c.py` 和对应测试**

- 在事务开始时预检目标政策：只要相关 statement/rule 非 DRAFT，或已存在 RuleTestCase，自动清理就返回明确的冲突错误并列出受保护 ID；不得部分删除后继续。
- 无受保护资产时，只删除自动生成的 DRAFT 数据及其子实体；ClauseRelation 和无关政策不动。
- 同一输入连续重抽两次，statement ID、条件关联、参数数量和全文哈希一致；rule ID 固定为 `RULE-` 加 `SHA-256(statementId)` 的前 32 位小写十六进制，同一 statement 重编译更新 DRAFT 内容而非制造递增副本。
- 非 DRAFT 规则或已有测试用例不得被自动改写、级联删除或静默降级。SQLite 未强制外键，因此引用完整性由上述服务层检查和回归保证。

### 4.5 增量 B：Nemo 编译器与叶子三态求值

**修改：`kg-system/app/rule_engine.py`、`app/pack2c.py`、`tests/test_pack2c.py`**

1. 按现有 `RuleEngine` 协议实现 Nemo 主引擎适配，ConclusionService 只实例化 Nemo；ProgramBuilder 输出 Nemo 语法，不再沿用 Cozo 模板。
2. Kùzu/现有查询层只提供条款、陈述、条件、例外、参数与优先级数据；不得把政策阈值编码为 Cypher `WHERE`。Nemo 负责规则派生、优先级传递闭包和成环检测，Python 负责叶子求值、事实完备性、数值比较、三态保护和解释组装。
3. `eval_condition()` 明确返回 `True/False/None`：缺事实一律为 None，包括 IN/contains；非法数值、单位不足、未知比较符和不可求值结构均为 None。只有实际比较失败才返回 False。
4. 主条件与例外条件分别注入 `true/false/unknown` 事实，空关系使用哨兵。Nemo 内部可表示 overridden，但公共输出只有三态：被可裁决的高优先级 APPLICABLE 规则覆盖时映射为 NOT_APPLICABLE；优先级依据不足或成环时为 UNABLE。UNABLE 不得覆盖其他规则，也不得被覆盖成 APPLICABLE。
5. `final_judge()` 严格按六步执行：确认与现行有效 → 模糊性 → 主条件 → 例外 → 优先级 → APPLICABLE。例外 unknown 必须 UNABLE；引擎异常、缺失输出或证明链不完整也必须 UNABLE，不能转成 NOT_APPLICABLE或静默 fallback。
6. 自动编译始终生成 `DRAFT`、`backTranslationMatch=null`、`testcaseIds=[]`。只有清单内政策可编译；leftOperand 必须是已定义属性路径或已注册 indicatorCode，否则拒绝生成可确认规则并记录原因。
7. 将现有 Cozo 测试改为真实 Nemo 测试，覆盖一级清单拦截、稳定 rule ID、同输入幂等、谓词命名、空例外、优先级闭包/成环和非 DRAFT 保护。

### 4.6 增量 B：statement 级判定、证明链与激活边界

**修改：`kg-system/app/conclusion.py`、`tests/test_conclusion.py`**

- `_compiled_rules_for()` 和 `_statements_for()` 改为 statement 级列表/映射，一条 clause 下多条 statement/rule 全部保留；每个输出携带 statementId、ruleId、clauseId 和 engine。
- 正式路径只允许同时满足以下不变量的 statement/rule：政策在清单内，statement 为 CONFIRMED 且有 confirmedBy/confirmedAt，rule 为 CONFIRMED、backTranslationMatch=true、testcaseIds 非空且引用有效；所引用测试须有 facts、expectedOutcome 和 authoredBy，expectedOutcome=UNABLE 时须有 expectedReason。缺任一项不得作为正式 Nemo 结论。
- 保留 legacy fallback v1 仅用于现有复数 API 兼容，逐项标记 `engine="fallback-v1"`、`formalReasoning=false`；混合路径顶层标为 `mixed`，不得再统称 `datalog-v2`。引擎异常不得转入 fallback。
- 公共输出补齐 `statementId/outcome/conditionMet/officiallyActivated/activationEvidenceId/reason/chain/evidenceIds/scopeNote/disclaimer`。`conditionMet` 只描述主条件三态：真、假或未知；例外未知时仍可为 true，但最终 outcome 为 UNABLE。
- `officiallyActivated` 默认 `UNKNOWN`，只有真实 `activationEvidenceId` 才能给出已启动状态；不得由 `conditionMet=true` 推断政策已经启动。
- chain 的每个已执行步骤均包含 `{step,ruleId,policyId,clauseId,citation,clausePath,clauseNo,factRef,quote}`，quote 必须在对应条款原文逐字定位。APPLICABLE 必须有完整六步和有效证明；否则降级 UNABLE。提前终止的 NOT_APPLICABLE/UNABLE 保留到决定性步骤，并给出明确原因。
- 新增回归：缺事实与条件为假的区分、非法数值、未知比较符、例外 unknown、多 statement 不折叠、模糊 statement 粒度、六步 quote/citation、无证明链降级、引擎失败、优先级覆盖/成环、激活状态不臆测和混合引擎标识。

### 4.7 增量 B：统一 API 契约且保留兼容

**修改：`kg-system/app/main.py`、`tests/test_api.py`；新增 `tests/test_stage2.py`**

- 新增 `POST /api/policy/judge`，与现有 `POST /api/policies/judge` 共用同一 ConclusionService，不复制判定逻辑。
- 单数接口严格接收 `{asOf,facts,question,maxHops=3}`：asOf 缺失、null 或非法均返回 422；maxHops 默认 3，允许 1–6，超出返回 422。响应为 `{outcomes,asOf}`，每个 outcome 使用上述 statement 级字段。
- 单数接口是正式推理契约：未确认 statement/rule 返回 UNABLE 和具体原因，不以 fallback v1 输出 APPLICABLE。
- 现有复数接口的请求、默认 asOf 和 `verdicts` 等兼容字段不变，可增加字段但不得无意删除；fallback 与正式结果必须逐项可区分。
- `scopeNote` 由实际 effective 查询覆盖范围、已收录/未收录引用生成，不照抄示例中的“37 份”；`evidenceIds` 只返回真实文档/证据 ID。固定免责声明为“辅助研究，不构成法律意见或官方解释”。

### 4.8 增量 B：隔离评测与机器可读报告

**新增：`kg-system/ontology_ly/capability/stage2_reasoning_smoke.json`**

固定技术情形、预期三态、预期理由、必要事实和来源哈希，标注 `datasetTier="technical-smoke"`。分两套报告，避免混合分母：

1. `POL0001` 端到端：三个品种分别命中对应 statement、条件不满足、缺品种事实、引用回链、范围说明和重复运行确定性。
2. 合成安全情形：集合缺事实、非法数值、未知比较符、例外未知、优先级覆盖/成环、多 statement、引擎失败和无证明链降级。

**新增：`kg-system/ontology_ly/tools/evaluate_stage2.py`；生成 `stage2_report.json`**

- 复用阶段 1 的快照隔离方式，复制 SQLite 到临时目录，所有确认状态、测试情形、Nemo 物化规则和缓存只写临时位置；评测前后比较正式数据库、规则资产与配置 SHA-256。
- 为验证正式引擎路径，可在隔离快照中构造明确标注 technical-smoke 的临时 CONFIRMED statement/rule 和测试情形；这些记录不写 `seed/business.json`、不写正式库，也不得被描述为专家确认。
- 通过真实 API/服务主链路执行，分别报告逐案 expected/actual、原因、chain、engine、scopeNote 和耗时；同一快照冷/热重复，比较除耗时外完整输出确定性。
- 指标口径固定：三态一致率=预测与期望一致数/总情形数；UNABLE 识别率=期望 UNABLE 且实际 UNABLE/期望 UNABLE 数；致命误判率=期望 UNABLE 但实际 APPLICABLE 数/期望 UNABLE 数；同时输出完整三态混淆矩阵。
- 解释可用率=具有决定性步骤、必填 chain 字段且 quote/citation 全部可回链的输出数/总输出数；范围标注完整率=具有真实 scopeNote 与 disclaimer 的输出数/总输出数。APPLICABLE 另设完整六步证明硬门。
- 技术硬门：三态一致率 ≥90%、UNABLE 识别率 ≥80%、UNABLE→APPLICABLE=0、解释可用率=100%、范围标注完整率=100%、APPLICABLE 证明链完整率=100%、重复输出确定、正式数据哈希不变、Nemo 真实执行无跳过。
- 报告分别列出 POL0001 与合成安全套件的分子/分母，不用合成样本冒充独立业务金标；延迟只形成本机技术基线，`productionPerformanceGate="NOT_ASSESSED"`。

## 5. 明确不做

- 不修改内核 29 类型，不扩市场包、运营功能或前端。
- 不在 2b 编译规则、自动确认陈述、推断 Scope 或生成 ClauseRelation。
- 不为提高指标调整阶段 1 检索权重，也不为让种子情形通过而篡改规则预期。
- 不实现任意复杂 AND/OR/NOT 条件树、单位换算或任意政策自动编译；遇到未支持结构返回 UNABLE。
- 不做 Cozo 自动降级、Soufflé/pyDatalog 回迁或把政策规则写进 Cypher/Python 阈值分支。
- 不把构造样本、临时 CONFIRMED 或技术通过率当作专家复核、法律意见、官方解释或生产性能验收。
