# 阶段 1：内核与检索基线增量建设

## 1. 摘要

依据 `kg-system/ontology_ly/方案定稿.md` 第 8 节，阶段 1 的冻结范围是：内核本体、别名表、解析分块、实体链接、混合检索、带引用问答，并且 Scope + Dimension 必须上线。

现有仓库已经实现上述主链路。本轮不重建本体、Scope 或 RAG，也不另起技术栈，而是补齐可重复、可审计、不会把依赖跳过误报为通过的基线：

1. 固定种子原文与人工核对的问题—相关段落金标；
2. 增加离线五模式检索、引用、确定性与延迟评测器；
3. 补解析分块、实体链接、API 边界和 Scope/Kùzu 回归；
4. 显式声明解析与 Kùzu 依赖，消除静默跳过；
5. 只对测试证实的缺陷做最小业务修复，生成真实阶段 1 基线报告。

本轮交付的是 **seed-smoke 回归基线**，不是十万文档、50 并发或真实业务召回率的生产验收。

## 2. 当前状态与边界

### 2.1 可直接复用

- `app/ontology.py`：`OntologyService.initialize()/sync()` 已接入启动流程。
- `app/scope.py`：10 维 Dimension、Scope 归一化去重、成员白名单和上位范围闭包已实现。
- `app/rag.py`：
  - `RagService.search()` 已实现 `naive/local/global/hybrid/mix`、RRF 融合和重排；
  - `EntityGraph.rank_segments()/relation_rank()`、`BM25Index.scores()` 提供图谱与关键词增强；
  - `_merge_ontology_aliases()` 已将本体别名、稳定身份和应用主键对齐接入检索；
  - `_answer()` 在无 LLM 时生成抽取式答案，`search()` 返回段落级 citations；
  - `_rows()` 已排除非“有效”来源文档。
- `app/documents.py`：TXT/Markdown、DOCX、PDF 抽取及 700 字分块已实现。
- `app/service.py`：`KnowledgeService.register_source()` 已登记段落号、页码、章节与字符位置。
- `ontology_ly/tools/build_alias_index.py`、`build_concept_alignment.py`：生成规则确定，不写生成时间戳，可做哈希重跑验证。
- `tests/test_api.py`、`test_scope.py`、`test_rag_alignment.py`：已有可复用 fixture 和基础覆盖。

### 2.2 已确认缺口

- `requirements.txt` 未声明 `python-docx`、`PyMuPDF`、`kuzu`，但代码和阶段 1 测试需要它们。
- `tests/test_scope.py::test_kuzu_projection_matches_sqlite` 使用 `importorskip`，缺依赖时会静默跳过。
- 当前没有问题—相关段落金标，也没有 Hit/Recall/MRR/nDCG、引用定位率、冷/热延迟和确定性报告。
- 没有独立的阶段 1 解析分块与五模式 RAG 回归测试。
- `DocumentIngestor._split_text()` 先扫描到全文最后一个 Markdown 标题，再把该标题赋给所有 chunk，章节定位存在明确缺陷。
- `/api/rag/query` 使用 `int(payload.get("topK") or 10)`，会把显式 `topK=0` 当成 10，与服务层最小值 1 的边界不一致。

### 2.3 明确不做

- 不重写 `app/rag.py` 的召回权重、融合公式或实体图结构；只有金标/回归暴露确定错误才最小修复，且不为了抬小金标过拟合。
- 不要求 Elasticsearch、MinIO、NebulaGraph、外部向量模型或 LLM；默认使用 relational + Hash 向量 + BM25 + lexical 重排。
- 不把 `capability/questions.json` 直接当检索金标，因为它没有相关段落标注且包含后续阶段能力。
- 不提前采用阶段 2c 的三态一致率、UNABLE 识别率、致命误判率门禁。
- 不修改前端页面，不新增政策规则编译、市场包或运营功能。
- 不强行消除别名表中的真实歧义；多目标写法继续保留冲突，并在实体链接时整条跳过。

### 3.2 建立人工核对的检索金标

**新增：`kg-system/ontology_ly/capability/stage1_retrieval_gold.json`**

数据源固定为 `seed/business.json` 中 4 份 SourceDoc、8 个 SourceDoc_Segment。每条记录采用：

```json
{
  "queryId": "S1-Q001",
  "query": "2025年早籼稻最低收购价是多少？",
  "relevantSegmentIds": ["SOU0001-S001"],
  "expectedEntityIds": [],
  "expectedOntologyIds": [],
  "tags": ["精确词", "政策"]
}
```

首批 10 条问题及人工相关段落如下：

| queryId | 问题 | relevantSegmentIds | 覆盖意图 |
|---|---|---|---|
| S1-Q001 | 2025年早籼稻最低收购价是多少？ | SOU0001-S001 | 精确词、政策、数值 |
| S1-Q002 | 最低收购价政策执行情况要加强什么工作？ | SOU0001-S002 | 段落定位、执行要求 |
| S1-Q003 | 2024年全国粮食播种面积和粮食产量是多少？ | SOU0002-S001 | 多指标、单段落 |
| S1-Q004 | 2024年稻谷、小麦、玉米和大豆产量分别是多少？ | SOU0002-S002 | 跨实体、多数值 |
| S1-Q005 | 2024年重庆粮食播种面积和总产量是多少？ | SOU0003-S001 | 地区区分 |
| S1-Q006 | 2024年重庆玉米产量是多少？ | SOU0003-S002 | 地区与品种组合 |
| S1-Q007 | What is world rice production for 2026/27 Sep? | SOU0004-S001 | 英文、全球情报 |
| S1-Q008 | China rice production for 2026/27 Sep, milled basis | SOU0004-S002 | 英文、口径 |
| S1-Q009 | 苞米产量是多少？ | SOU0002-S002 | “苞米→玉米”别名链接 |
| S1-Q010 | 全国与重庆2024年稻谷产量分别是多少？ | SOU0002-S002、SOU0003-S002 | 跨文档、多相关段落 |

标注只依据上述原文和主数据稳定身份，不根据当前检索结果反填。`expectedEntityIds/expectedOntologyIds` 仅在种子主数据或对齐台账中能明确核对时填写；无法确认的保持空数组，不猜测。文件同时记录 `schemaVersion`、`stage: "Stage 1"`、`datasetTier: "seed-smoke"` 和来源说明。

### 3.3 新增离线评测器与机器可读报告

**新增：`kg-system/ontology_ly/tools/evaluate_stage1.py`**

提供三个清晰入口：

- `evaluate_retrieval(service, gold)`：复用真实 `RagService.search()`，逐模式、逐问题评测；
- `verify_citations(result, db)`：将响应引用与 SQLite 原文及答案编号交叉核验；
- `main()`：建立隔离快照、执行评测、计算硬门禁并写报告。

固定评测口径：

1. 默认读取 `data/grain_oil.db`，计算 SHA-256 后复制到独立临时目录；所有索引写入临时 `data_dir`，不得改写原库、`data/rag/config.json`、现有向量缓存或实体抽取文件。
2. 临时配置显式固定为 `embeddingBackend=hash`、`rerankMode=lexical`、无 LLM、无 LLM 实体抽取；不向报告输出任何 API Key。
3. 五种模式均执行，`topK=10`、`answer=True`。Hit@5/10、Recall@5/10、MRR@10、nDCG@10 以 `items.segmentId` 与金标计算；Recall 对多相关段落取命中数/相关段落总数，nDCG 使用二元相关性和理想排序归一化。
4. 同时报告 `zeroResultRate`（返回 items 为空）与 `zeroHitRate`（没有相关段落命中），避免“零召回”语义混淆。
5. 引用核验必须达到：docId/segmentId 存在且文档有效；quote 非空、不超过 200 字且是原 segmentText 的逐字子串；pageNo/chapterPath/segmentNo 与数据库一致；引用顺序对应检索 items；离线抽取式答案中的每个 `【n】` 均能映射到第 n 条引用，且相应原文摘句出现在答案中。
6. 每种模式记录第一次冷查询；同一实例将全部金标重复执行 3 轮作为热查询，使用 `perf_counter` 记录毫秒，分别输出 P50/P95/max。第二轮与第三轮逐项比较 segmentId 排名，生成 `deterministicRanking`。
7. 报告包含 Python/OS、SQLite 快照哈希、金标哈希、图谱后端、embedding 后端与模型、重排模式、Scope 统计、逐问题排名与指标、引用失败明细和门禁结果。

**新增生成物：`kg-system/ontology_ly/tools/stage1_report.json`**

只能由评测器生成。首轮流式记录真实指标，不倒填目标值。硬门禁设为：

- 五模式均成功执行；
- seed-smoke 的 `Hit@10 = 1.0`，仅作“已知原文可被找回”的回归门；
- 引用结构与原文定位率 `= 1.0`；
- `deterministicRanking = true`；
- 金标引用的段落均存在且有效；
- Scope `dimensionCount = 10`。

Recall/MRR/nDCG 首轮只形成基线，不虚构“真实业务召回 ≥90%”。报告明确写入：

- `datasetTier: "seed-smoke"`；
- `businessQualityGate: "NOT_ASSESSED"`；
- `productionPerformanceGate: "NOT_ASSESSED"`。

《需求文档》8.1 的原文门槛保留为后续生产验收依据：常用查询 P95 ≤ 3 秒（并发 50），全文检索 P95 ≤ 1 秒。本机小样本冷/热数据不得被解释为已满足这两个生产指标。

### 3.4 补阶段 1 回归测试

**新增：`kg-system/tests/test_stage1.py`**

复用 `tests/test_api.py` 的 Settings/TestClient 模式，覆盖：

1. 解析与分块：空文本、CRLF、段落合并、700/701 字边界、超长段落所有 chunk 均不超限；Markdown 不同章节不得共用文末标题；DOCX 标题与正文 chapterPath；临时生成两页 PDF 并验证 pageNo=1/2 与 pageCount=2。
2. RAG 服务：五模式 smoke；非法 mode 回退 hybrid；topK 最小 1、最大 50；空查询 ValueError；Hash 后端同输入重复排名一致；作废文档刷新后不进入 `_rows()` 和检索结果。

4. 引用：离线抽取式答案的 `【1】…【n】`、citations、items 和 SourceDoc_Segment 可逐字回溯，页码与章节不丢失。

- NO_APP_TABLE/NO_APP_RECORD 仅在具有稳定 targetIdHint 时保留本体身份；
- 已有应用主数据身份不被别名覆盖。

**保留：`kg-system/tests/test_scope.py`**

不放宽现有断言；安装依赖后单独运行 Kùzu 投影用例，确认不是 skipped。

### 3.5 最小修复已确认缺陷

**文件：`kg-system/app/documents.py`**

调整 `_split_text()` 为按 Markdown 标题分节后再调用 `_chunk_text()`：flush 前一节时使用前一节标题，新标题只影响后续内容；无标题文本保持 `chapterPath=None`。不改变 700 字限制、DOCX/PDF 接口或返回结构。

**文件：`kg-system/app/main.py`**

仅修正 `/api/rag/query` 的 topK 缺省解析：缺省、null 或空字符串使用 10，显式数值（包括 0 和负数）传给 `RagService.search()` 统一 clamp，避免 API 与服务层边界不一致。非法整数仍按现有 ValueError → 422 处理。

若新增测试还发现其他确定性错误，先以失败用例证明，再做同范围最小修改；不借本轮调整检索权重或增加新功能。

## 5. 假设与决定

- 以当前 `方案定稿.md` 为阶段边界，以《需求文档》8.1 为生产性能原始口径，不自行放宽为“平均 ≤3 秒”。
- 默认离线 Hash + BM25 + relational 是本轮唯一必测检索路径；外部服务是可选集成，不是阶段 1 基线前置条件。
- 种子金标用于防回归，不用于宣称业务质量；后续若要设真实 Recall/MRR/nDCG 门槛，必须另建固定真实文档快照与更大规模人工金标。
- 本报告不评估 LLM 答案语义质量，只验证当前无 LLM 抽取式答案及其引用链。
