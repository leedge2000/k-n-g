## 0. 一句话结论

合并版可以作为**项目总纲与对外沟通稿**，但不能直接当**实施基线**——它停在"对象清单"粒度和"选型四选一"，缺字段、缺 ID、缺校验门，且存储选型与已定决策冲突。

我的方案 = **合并版的骨架 + Stage 0 的落地契约 + 一处重大增量（政策条款级推理）**。

增量部分我给出 9 个新对象类型的逐字段定义，并明确它们**全部属于政策包，内核 29 个保持不变**。

## 2. 三处硬冲突与裁决

### 2.1 存储：不用 PostgreSQL / Neo4j，用 SQLite + Kùzu + 现有 RAG

合并版给的是「MVP：PostgreSQL + 边表 + pgvector；规模化：Neo4j + 专用向量库」。这与现状和已定决策冲突：

| 合并版组件 | 我的选择 | 理由 |
|---|---|---|
| PostgreSQL（元数据/本体版本/审核） | **SQLite** | 现有系统已是 SQLite；本阶段数据量（数万节点、数十万数据点）SQLite 完全够；迁移是纯成本 |
| Neo4j 或 PG 边表（图） | **Kùzu** | 已定；嵌入式、无服务、列存、Cypher |
| pgvector / 专用向量库 | **现有 RAG 索引** | hash/openai 向量 + BM25 + RRF 已在跑，不重复建设 |
| 专用时序库 | **SQLite 表** | 价格/统计是「序列 × 期间」的规则二维表，SQLite 索引足够；时序库的压缩优势在百万级以上才显现 |
| 规则库 | **Datalog 规则文件 + SQLite 存审核状态** | 规则是文本资产，用文件版本化更合适 |
| 文档存储 | **本地文件系统**（已有 upload 目录） | 已有原件存储与 `?token=` 下载链路 |

**净结果：组件从 6 个降到 4 个**（SQLite、Kùzu、RAG 索引、Datalog 引擎），且无新增运维负担。

**升级触发条件**（写死，避免提前优化）：
- 迁 PostgreSQL：并发写 > 50 QPS，或单表 > 500 万行。
- 迁 Neo4j：Kùzu 路径查询 P95 > 500ms 且已做索引优化。
- 上专用向量库：向量条数 > 200 万且召回率成为瓶颈。

### 2.2 对象类型：内核 29 不动，条款级 9 个全部进政策包

合并版说"内核控制在几十个类型"，条款级只给了 8 个"积木"（条款、规范陈述、主体、行为与对象、前提条件、例外、后果、参数、条款间关系），没落成类型。

**裁决**：这些积木**不是内核对象**，是政策包的专用模型。理由：

1. 它们只服务政策条款，市场包和检索层不需要知道 `Condition` 是什么。
2. 放进内核会让内核从 29 涨到 38，违反"包不越权"的反向约束（内核膨胀）。
3. 条款模型会随法规体系变化，变更频率远高于内核，混在一起会让内核版本号失去意义。

### 2.3 规则表示：选 Datalog，不选 ASP / LegalRuleML / SHACL

合并版列了四条路线让阶段 0 选。我给明确推荐；阶段 0 已按收窄范围跑完，结论如下。

**推荐：Datalog（Nemo 为主，Cozo 为备，pyDatalog 退出）**

Datalog 仍是范式选型；引擎已由阶段 0 实测替换——最初设想的主引擎 Soufflé 在 Windows 上需要 Docker 或自行编译，部署成本不划算，故排除。

| 候选 | 判定 | 理由 |
|---|---|---|
| Datalog · **Nemo** 0.10.1 | **选（主）** | 证明树天然对应"逐步指向原文"的解释要求；分层否定（`~`）能表达"除……外"；pip 原生 Windows 轮子，无 Docker、无编译；本体推理是它的原生场景；11 情形 × 3 条款实测 1.4 ms，1000 条 × 3 条款 2.4 ms |
| Datalog · **Cozo** 0.7.6 | **备** | 单文件嵌入式（`cozo_embedded`），无外部进程；同样支持分层否定与递归；作为 Nemo 出现平台兼容问题时的等价替代 |
| Soufflé | 排除 | 与 Nemo 同路线，但 Windows 需 Docker/WSL 或自建工具链；本场景规模（单条规则 < 50 节点）用不到它的编译期优化 |
| pyDatalog | 排除 | 2018 年停更，不兼容 Python 3.12；仅作历史对照保留 |
| ASP（答案集编程） | 备选升级 | 只在"规则本身需要多解/缺省推理"时才考虑；学习曲线陡、团队上手慢 |
| LegalRuleML / Catala | 排除 | XML 生态重、工具链弱、中文法条适配几乎为零；投入产出比不成立 |
| SHACL | 排除 | 本质是**约束校验**（闭合世界检查），不是推理；拿它做"适用性判定"会写成大量手工开关 |

**Datalog 的已知局限与对策**：

| 局限 | 对策 |
|---|---|
| 不能做数值聚合与算术推导 | 数值先在时序库/计算函数里算成布尔事实，再注入（如 `price_below_threshold("小麦","2025-06-01")` 由服务层计算后作为事实输入） |
| 无法区分"事实不成立"与"事实缺失" | 事实完备性由服务层判定，缺失即返回 `UNABLE`，不交给引擎猜 |
| 优先级需显式建模 | `prevails(?a, ?b)` 谓词 + 线性递归传递闭包 + `cycle(?a) :- prevails_t(?a, ?a)` 成环检测；优先级依据来自 `ClauseRelation.priorityBasis`。已实测多跳覆盖与成环拦截 |
| 闭包推理可能不终止 | 强制规则分层（stratification）；优先级图在**规则包加载期**跑一次成环探测，有环即拒绝启动 |
| 多条款同时成立时结论会相互覆盖 | 覆盖消解在结论层做第二遍：只有自身 `APPLICABLE` 的条款才有资格覆盖他人，`UNABLE` 双边不可让渡 |

**阶段 0 试验（已完成）**：
- 样本：《小麦和稻谷最低收购价执行预案》第五条第一款（1 份一级政策）。
- 路线：pyDatalog / Nemo / Cozo 三路同源事实，7 情形全部 7/7 一致；后以 Nemo 为主引擎增验多条款优先级（11 情形 11/11）。
- 产出：`packs/policy/rule_trial/` 下的规则模板、情形集与实测报告，结论见该目录 `REPORT.md` §9/§10。

**引擎选型溯源**：2026-11-13 由「Soufflé 主 / pyDatalog 后备」改为「Nemo 主 / Cozo 备 / pyDatalog 退出」，依据是阶段 0 实测（部署成本与 Windows 兼容性），非范式变更。

## 5. 三态结论的判定算法

合并版给了三态的定义，但没给判定顺序。顺序错了会出现"用例外否掉一条本来不适用的规则"这类错误。我的判定顺序：

```
judge(statement, facts, asOf):
  1. 取 asOf 时点有效 且 confirmationStatus = CONFIRMED 的 statement
     否则 → UNABLE(reason = 规则未确认)
  2. if vaguenessFlag → UNABLE(reason = 含模糊用语, note = vaguenessNote)
  3. 求 conditionId 条件树：
     a. 收集所有叶子所需事实
     b. 任一叶子事实缺失 → UNABLE(reason = 缺事实, 列出缺失项)
     c. 求值为 FALSE → NOT_APPLICABLE(reason = 前提不满足, 指出哪个叶子)
  4. 前提为 TRUE，检查 exceptionIds：
     a. 任一例外条件为 TRUE → NOT_APPLICABLE(reason = 被例外排除)
     b. 例外条件缺事实 → UNABLE(reason = 例外无法判定)
  5. 检查优先级冲突：
     若存在 prevails 关系且更高优先级规则给出相反结论
       → 按 priorityBasis 裁决
       → 无法裁决（同一依据层级）→ UNABLE(reason = 规则冲突)
  6. → APPLICABLE(consequence, 推理链)
```

**推理链要求**：每一步输出 `{step, ruleId, factRef, clausePath, quote}`。`quote` 必须能在原文定位（复用 Stage 0 门 1 的 G1-2）。

**为什么要先判"未确认"再判模糊**：未确认规则可能根本不该参与推理，先筛掉能避免用一条草稿规则去判模糊用语。

## 6. "理论满足 ≠ 已启动"的字段落地

合并版提了这条但没给结构。落地成结论对象的两个独立字段：

```json
{
  "outcome": "APPLICABLE",
  "conditionMet": true,
  "officiallyActivated": "UNKNOWN",
  "activationEvidenceId": null,
  "scopeNote": "依据已收录的 37 份文件；引用但未收录：发改价格〔2023〕XXX 号",
  "disclaimer": "辅助研究，不构成法律意见或官方解释"
}
```

`officiallyActivated` 判定规则：

| 值 | 条件 |
|---|---|
| `TRUE` | 存在 `Event`（`eventTypeId` 为启动公告类）且 `ACTIVATES` 边指向该 statement，且有 `Evidence` |
| `FALSE` | 同上的启动公告明确否定（如"暂不启动"） |
| `UNKNOWN` | 无公告证据（**默认值，不得默认 TRUE**） |

**这一条是我对合并版最看重的补充**：不落成字段，模型很容易把"条件满足"直接说成"已经启动"，这是政策类问答最危险的错误。

## 7. 推理引擎与 Kùzu 的分工

这是合并版没讲、但实施时最容易踩坑的地方。

| 环节 | 谁做 | 为什么 |
|---|---|---|
| 条款/陈述/条件的存储与查询 | Kùzu | 图结构天然 |
| 条件树求值 | **规则引擎** | Cypher 无分层否定、无证明树 |
| 优先级裁决 | **规则引擎** | 需要 `prevails` 谓词与分层 |
| 事实汇集 | **服务层** | 用户输入 + 图属性 + 时序值三源合并 |
| 数值比较 | **服务层/计算函数** | 先算成布尔事实再注入 |
| 结论与解释生成 | **规则引擎 + 解释服务** | 证明树 → 推理链 |

**边界铁律**：Kùzu 只负责"取子图"，绝不承担推理。每次判定前，服务层按 `statementId` 抽出相关子图（条款 + 条件 + 例外 + 参数 + 优先级关系），序列化为事实集，喂给 Datalog 引擎。子图规模小（单条规则通常 < 50 个节点），导出成本可忽略。

**反对做法**：把规则编码成 Cypher 的 `WHERE` 子句。短期看省事，长期会导致：无法表达"缺事实 → 无法判定"（Cypher 只会返回空集）、无法输出证明树、规则与本体版本无法独立演进。

| 2a 政策文档级 | 政策抽取、适用范围、版本链、现行有效查询 | 不变 |

| 2c 形式化与推理 | 一级政策规则编译、推理引擎、情形判定器、解释服务 | 补：**先做 1 份政策的端到端**（合并版已建议），且验收看三态一致率（§9） |

| 5 运营 | 增量入库、本体与规则演进、质量监控 | 不变 |

**我不同意的一点**：合并版把 2c 说成"不确定性最大，建议先用一份核心政策试点"。我认为不确定性不在于"能不能编译"，而在于**专家确认的时间成本**。一份一级政策的规则确认通常需要政策法规专家 3—5 轮评审。所以 2c 的真实瓶颈是**专家排期**，不是技术。建议在阶段 0 就把专家的评审时段锁进日历，否则 2c 会无限期停在"规则待确认"。

## 9. 验收口径：三态一致率而非通过率

合并版说"规则测试通过率"。这个指标有漏洞：如果测试情形里 `UNABLE` 极少，模型可以靠"全部判 APPLICABLE"刷高通过率。

我的口径：

| 指标 | 定义 | 说明 |
|---|---|---|
| 三态一致率 | `(判对 APPLICABLE + 判对 NOT_APPLICABLE + 判对 UNABLE) / 总情形` | 主指标 |
| UNABLE 识别率 | 应判 UNABLE 的情形中被正确判为 UNABLE 的比例 | **单列，防止刷分** |
| 误判致命率 | 把 UNABLE 判成 APPLICABLE 的比例 | **必须为 0**，这是最危险的错误 |
| 解释可用率 | 推理链每一步都能定位到原文的比例 | |
| 范围标注完整率 | 结论带 `scopeNote` 且列出未收录文件的比例 | |

**基线建议**（阶段 0 与业务方确认）：三态一致率 ≥ 90%，UNABLE 识别率 ≥ 80%，误判致命率 = 0。

## 10. 能力问题从 24 条扩到 30 条

合并版要求"三类各至少 10 条"。我在 Stage 0 的 24 条基础上补 6 条**条款适用性**问题（新增 E 组）：

| 编号 | 问题 | 依赖 | 跳数 |
|---|---|---|---|
| E1 | 某企业某地某时收购某品种，适用哪些条款？ | NormativeStatement + Scope + Condition | 3 |
| E2 | 当前价格水平下，哪些预案的触发条件已满足？ | Condition(TIME_SERIES) + 计算函数 | 2 |
| E3 | 某条款适用后须承担什么义务，违反什么后果？ | NormativeStatement + Consequence | 2 |
| E4 | 两份政策中哪些条款相互矛盾或重复？ | ClauseRelation(PREVAILS_OVER/CITES) | 2 |

E1—E6 全部要求能定位到 `clausePath` + 原文摘句，否则不计通过。
